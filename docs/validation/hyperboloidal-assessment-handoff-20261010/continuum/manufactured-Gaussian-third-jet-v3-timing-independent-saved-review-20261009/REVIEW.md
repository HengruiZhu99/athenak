# Gaussian v3 timing: independent saved audit and cost assessment

The completed v3 timing stage passes this saved-only audit. Its compact result reports 20 records, 11,816 identity rows, 1,692 precision rows and zero failures. Forty ordered begin/complete progress lines independently bind the ten declared event keys at 180 and 220 digits. The child, outer and root receipts accept exactly this timing stage, with unchanged source/runtime/review pins and matching output hashes. All 625 unique protected pins were rehashed. The root took 55.79448625 s; the child took 54.938825625 s, within the 600/660/690 s limits.

This audit froze 54 compact inputs before reading their content. It hashes the two JSONL payloads and height-context file without decoding them. Therefore it checks the identity/precision totals and absence of failures as reported; it does not independently recount their rows, obtain a maximum passing residual, or certify a uniform absolute forward error. The original v2 timing remains COMPLETE FAIL with six connection-identity failures. The higher precision v3 pass is a new scoped result, not a revision of that failure.

The fixed full registry contains 2,505 records per precision: 8 origins, 312 positive-radius core-bin events, 1,248 transition-bin events, 936 outer-bin events and one negative control. These are exact **nominal-radius bookkeeping bins**, not measured branch counts for an unexecuted full run: reconstructed multiprecision norms can straddle a nominal cutoff endpoint. The full registry has 1,880 nominal finite-radius eligible valid events per precision and 470,752 precision-component comparisons. All 5,010 records remain held.

The event-time sum in the timing run is 36.735805289 s. The other root time is 19.058680961 s, predominantly the two fixed height/context setups and source/provenance work. Multiplying all root time by 5,010/20 would repeat that setup and gives 13,976.52 s. Instead, weighting the observed per-precision event times by the nominal bins, and retaining measured setup once, gives empirical minimum/mean/maximum scenarios of **10,376.54 / 10,881.09 / 11,432.94 s** (about 2.88–3.18 h). These are scenarios, not confidence intervals or rigorous runtime bounds. A 25% inflation of the maximum-bin event scenario gives 14,286.41 s, only 113.59 s below the unchanged 14,400 s soft cap.

Only one positive-radius core event and three events each in the transition and outer bins were timed per precision. No nonorigin epsilon-zero case was timed. Unmeasured directions, times, scalar inverse iterations, Gaussian regime changes, endpoint branch selection, scheduling and larger output volume can change runtime. The source still computes the raw graph/physical-curvature diagnostics even where their admission gates are false. The timing sample therefore supports a practical bounded full attempt, but does not guarantee completion within the cap. Root must separately decide cost admission; `cost-assessment.json` deliberately leaves `full_stage_cost_admission=false`.

The source/math review of the full fixed protocol remains the separately pinned v3 source review. This timing audit admits no native queries, coupled inner BM solution, global slicing, inverse coverage, propagation or black-hole stability conclusion.

One reviewer failure is preserved: attempt001 assumed that the root invocation used an `environment` key; the actual root record uses `fixed_environment`. It stopped before output validation with `KeyError`. The fresh reader v2 changes only that metadata-key selection and passes. Two earlier shell reads guessed missing filenames; they made no data or source changes. All original owner and root bytes remain unchanged.

The successful saved-only reader ran with explicit `PYTHONOPTIMIZE=0`, bytecode disabled, single-thread variables and `python3 -I -B`. Its exact command, runtime, input capture and original failure are retained. No candidate module or target arithmetic was executed.
